# 계산 개념 요약

- Topic 목록 집계: ROS2 Graph에서 실제 발견된 Topic을 이름과 type으로 정리한다.
- Topic raw endpoint 수: Dashboard endpoint를 포함한 Publisher/Subscriber 수다.
- Topic Node 수: 같은 역할의 고유 Node 수이며 기본 목록에서는 내부 Monitor Node를 제외한다.
- Topic Graph 상태: `active`, `no_subscriber`, `waiting_publisher`, `inactive`를 구분한다.
- Topic 대표 상태: deep monitoring 수신 결과의 `never_received`/`stale`을 Graph 상태와 합치며 command는 Graph 상태를 유지한다.
- Topic Hz: 최근 window에 남은 메시지 수를 전체 `hz_window_sec`로 나눈다.
- Topic age: 현재 시각에서 마지막 수신 시각을 뺀다.
- Service 상태: 유효한 type에서 Server가 있으면 `active`, Client만 있으면 `waiting_server`, 둘 다 없으면 `inactive`다.
- Action 상태: 유효한 type에서 Server가 있으면 `active`, Client만 있으면 `waiting_server`, 둘 다 없으면 `inactive`다.
- Node 상태: Graph에서 보이면 `active`, 이전 발견 뒤 debounce를 거쳐 사라지면 `disconnected`다.
- 실행 시간: 각 실행 Runtime이 시작·종료 시각 차이를 밀리초로 저장한다.
- Alert: Monitor가 후보를 만들고 Backend가 active/resolved/recurrence를 MariaDB와 동기화한다.
- Snapshot: Monitor가 Topic·Service·Action·Node·Alert를 같은 시점에 조립하고 Backend가 마지막 정상값을 cache한다.

현재 Graph 갱신 순서는 `ros_monitor.py RosMonitor._update_graph()` L346-L353의
Node → Topic → Service → Action이다. rclpy spin은 이미 등록된 timer와 subscription/action callback을
실행하며 timer를 새로 설정하는 역할은 아니다.

## QoS

- Reliability: `RELIABLE` 또는 `BEST_EFFORT`
- Durability: `VOLATILE` 또는 `TRANSIENT_LOCAL`
- History: `KEEP_LAST` 또는 `KEEP_ALL`
- Depth: KEEP_LAST에서 보관할 샘플 수
- Deadline, Lifespan, Liveliness, Lease Duration: duration·생존 정책
- Topic Auto: 반대 역할의 외부 Graph endpoint와 가장 많이 호환되는 profile 선택
- Service Auto: Fast DDS server Request Reader와 Response Writer를 한 Client profile로 만족하도록 선택
- Action Auto: Goal/Result/Cancel Service와 Feedback/Status Topic의 5개 profile을 따로 선택

Monitor는 미수신이나 timeout만으로 QoS 불일치를 확정하지 않는다. 확정 `incompatible`만 설정된 연속
Graph 갱신 횟수를 거쳐 QoS Alert가 된다.
